# R13: Live RGB engine

Status: software implementation complete; prolonged physical USB run pending.

## Engine model

`mechkeymesh-lighting-engine` renders device-independent scenes against layout geometry. A scene contains ordered layers with:

- type: Static, Animation, Reactive or Audio
- enabled state
- opacity
- Replace, Add, Multiply or Screen blend mode
- an optional physical-key ID mask
- stable order
- primary and secondary colors
- speed and width parameters

The initial effect set is key highlight, ripple, meteor, lightning, wave, trail, breathing, gradient, rain and sparkle. Static is also available as the base layer primitive. Rendering is deterministic for a fixed scene, layout and input.

Reactive effects can be exercised from the editor by triggering a physical key. This tests the renderer without installing a global keyboard hook.

## F108 USB streaming

The wired implementation follows the public F108 SignalRGB sender:

- [`ThePrimeDev/SignalRgb_AulaF108Pro`, cabled implementation](https://github.com/ThePrimeDev/SignalRgb_AulaF108Pro/blob/main/Aula%20F108%20Pro%20Cabled)
- [`parsiya/f108-pro`, protocol catalog](https://github.com/parsiya/f108-pro/blob/main/ai-docs/hid-protocol.md)

Each frame is fully serialized and validated before the first report is sent:

1. `04 20`, byte 8 = `08`, then correlated command echo or ACK
2. seven 64-byte feature reports containing `[LED index, R, G, B]` records
3. one empty feature report
4. `04 02`, then correlated command echo or ACK

Alpha.4 corrects the clearing-report count and scopes reply validation to the transmitted command, following the capture-based [reference sender](https://github.com/Punkster81/AULA-F108-Driver/blob/main/aula_f108_pro_final.py). Failed streaming remains stopped across reconnect until an explicit Live RGB or Music start. See [alpha.4 evidence](F108-2026-10-13-ALPHA4.md); physical streaming remains unverified.

This is the volatile real-time preview family. It does not use the persistent per-key RGB transaction and does not repeatedly rewrite onboard lighting memory.

Live RGB is exposed only for the wired USB descriptor. It remains hidden on the 2.4 GHz descriptor because the verified wireless transport uses a different 32-byte report format and no equivalent live path has been physically proven.

## Backpressure and background operation

The render thread runs independently of the webview, so minimizing the window does not pause it. The device manager owns a single latest-frame slot:

- a newly rendered frame replaces an unsent frame
- replacement increments the coalesced-frame counter
- only the device-manager thread writes HID reports
- no unbounded per-frame channel can form
- transport errors stop the renderer and enter normal device recovery when required

The editor exposes submitted, sent, coalesced, failed and buffered frame telemetry.

## Light zones

R13 targets the main key LED indices from the OEM layout. It does not claim control of the side strips or the light bar above the arrow cluster. Those zones remain separate until their mapped commands are integrated and verified in this codebase.

## Required physical run

1. Start live RGB over USB and exercise every initial effect.
2. Confirm masks, opacity, all blend modes and layer reordering on hardware.
3. Minimize and restore the application while streaming.
4. Saturate the renderer above transport throughput and confirm the queue remains at one frame.
5. Run continuously for several hours while watching sent, coalesced and failed counters.
6. Confirm the keyboard remains connected and stored onboard lighting was not changed.
7. Switch to 2.4 GHz and confirm the Live RGB navigation and commands disappear or reject safely.

Until this run is recorded, R13 is not physically verified.
