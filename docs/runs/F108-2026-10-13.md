# F108 Pro feedback and clock readback hotfix

Build: 0.20.0-alpha.2, based on the R19 application-picker branch. This preserves the original transparent artwork and application picker.

## User evidence

The user connected an AULA F108 Pro over USB. SQLite reported schema 5, WAL and integrity OK. The device was detected through `aula.f108pro` with configuration matchers `0C45:800A usage FF13` and `05AC:024F usage FF60`.

| Operation | Runtime result | Physical result reported by user |
| --- | --- | --- |
| Upload macro bank | Failed: acknowledgment byte 3 = `0xFF` | Not reported |
| Apply normal-layer keymap | Failed: acknowledgment byte 3 = `0xFF` | Not reported |
| Apply Fn-layer keymap | Failed: acknowledgment byte 3 = `0xFF` | Not reported |
| Apply built-in lighting | Failed: acknowledgment byte 3 = `0xFF` | Not reported |
| Apply stored per-key RGB | Failed: acknowledgment byte 3 = `0xFF` | Not reported |
| LCD media upload, twice | Completed | Not reported |
| Sync LCD clock | Failed: acknowledgment byte 3 = `0x1A` | User explicitly confirmed that the clock changed successfully |
| Knob controls | Missing from app | No user-firmware action capture yet |

The clock warning is a false failure relative to the observed physical result. The other warnings cannot be classified as rejection or success from one reply byte alone.

## Source and interpretation

The reference sender places `year % 2000` in clock payload byte 3 and performs a readback before the final `04 02` apply. In 2026 that value is 26 (`0x1A`). Our shared validator incorrectly required that byte to equal `0x01` for every readback. A returned clock-data echo is consistent with the warning; the original log does not include the complete response, so an exact echo remains an interpretation pending the new build's hardware test.

## Changes

- Clock data uses a distinct readback path. A complete 64-byte matching echo is accepted; the existing command ACK form remains supported. A year byte on its own is insufficient. The required readback, delay and final apply remain in sequence.
- `0xFF` is not accepted globally. Failed feature readbacks now include the sent prefix and 16 returned bytes, identifying the phase and exposing response structure for the remaining warnings.
- Windows feature reads reject incomplete buffers or unexpected report IDs, including the shorter stored-RGB readback prefix.
- A visible Knob page lists the reference firmware actions, Fn + knob mode switching and the absence of a verified remapping command. It does not claim to observe the selected mode or to configure custom assignments.

## Validation and next physical check

Regression tests cover a 2026 clock echo reaching the apply command, a corrupted echo stopping before apply, legacy ACK compatibility, unrelated zero/FF replies, and feature-report length/report-ID normalization. Core tests, clippy, frontend syntax, format and original branding are checked before delivery. Windows CI verifies the full workspace and builds the executable.

On the new build, sync the clock and compare both the visible clock and Runtime log. Then share the expanded `0xFF` warnings and report whether an obvious normal-key remap and lighting change physically take effect. The new Knob page is guidance; arbitrary knob remapping and R18 physical captures remain pending.
