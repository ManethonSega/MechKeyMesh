# Alpha.4: Macro library and RGB feedback

Baseline: alpha.3, commit 668489803e1977f6ab18c95d329bc7241ecb124d.

## User evidence

At 15:55 CEST the startup macro bank, normal keymap, Fn keymap and built-in lighting transfers completed. Stored per-key RGB failed after its data transfer, with sixteen reported zero reply bytes. Live RGB subsequently returned `04 20 00 00 ... 08`, `04 02 00 FF ...` and `04 02 00 00 ...`, repeatedly recovering/reopening the USB device. Three later built-in lighting operations completed. A device presence check also timed out. These are transfer results, not physical key/lighting confirmations.

The supplied image shows the Saved macros panel empty, an empty current timeline, JSON text in the import/export panel, and a manual macro upload error after 3000 ms. New and Duplicate originally changed an editor draft without inserting a saved entry into the left list. Macro status appeared at the bottom beside the hardware upload button. The screenshot does not establish that JSON was imported into the editor.

## Changes

- New and Duplicate save a visible local macro entry. Pending edits are saved when changing selection, creating/copying or uploading; failed local saves stop that action. Delete requires a saved selection. Local-save buttons serialize concurrent saves, and upload progress does not disable local editing. Status is shown beside the list. Changing selection updates the JSON panel too.
- Manual macro upload uses a blocking worker from an async Tauri command, keeping USB waits off the UI event thread. Macro upload has a separate finite 15-second queue/execution timeout instead of the general 3-second command limit. Cancellation remains supported.
- Stored RGB data readback accepts a complete matching first/last transmitted report, including a matching zero-filled table, or the existing ACK form. Unrelated zero/FF replies remain failures. Final apply still requires its command ACK. Flash finalization does not request an ACK; the sender waits 300 ms after the preamble flash write and 800 ms after the final write.
- Live RGB uses seven colour reports plus one clearing report, matching the `04 20` argument of eight. It previously sent two clearing reports. The two required command readbacks remain; each must match a complete sent command echo or an ACK for the same command. FF, unrelated replies and damaged echoes remain errors.
- A live failure is retained across USB recovery. The next renderer submission fails and stops the producer rather than automatically resubmitting after fast reconnect. Explicit Live RGB or Music start clears the retained failure. Status exposes the transport error.

## Reference evidence and limits

Primary source: https://github.com/Punkster81/AULA-F108-Driver/blob/main/aula_f108_pro_final.py

The reference `_send_frame` sends seven colour chunks, one zero report and apply, with feature readbacks at start/apply; it does not impose a universal byte-3 ACK value. Its flash path documents no ACK after F0 and settling delays. The source's hardcoded historical date-shaped unlock packets are not copied. The existing verified command families, separate clock sync and LED indices are preserved. The reference MIT notice is included.

## Verification

Core regressions cover complete live frame count and correlated echoes, invalid replies, matching zero RGB data reaching apply/flash, no flash readback, failure staying stopped after reconnect, explicit restart and separate macro deadlines. The shared macro UI interaction suite exercises New, Save, Duplicate, selection, Delete, reload and editing during a pending/failed hardware upload. It passes locally against the actual HTML/JavaScript in a DOM environment; CI runs the same assertions in Chrome and captures a synthetic UI screenshot. Local browser launch is blocked by the execution environment.

Rust workspace tests, clippy, frontend syntax, formatting and original transparent artwork are checked before packaging. Windows CI compiles the desktop command bridge and executable. Physical stored-RGB persistence and live RGB effects still require testing on this user's keyboard. Completion logs alone do not establish physical behavior.
