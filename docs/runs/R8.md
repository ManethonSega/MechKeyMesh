# R8: Stored per-key RGB

## Status

**IN PROGRESS**

R8 implements persistent physical-key color editing and translates stable layout keys into device-specific LED indices.

## Architecture

The generic model is:

```text
Physical key ID
      |
      v
Layout LED index
      |
      v
RGB
      |
      v
driver packet translation
```

The application never assumes that a HID usage, matrix position, device key index and LED index are interchangeable.

### Stored RGB sender

The OEM stored-RGB sender at `FUN_0044b910` performs two transactions.

Brightness/setup preamble:

```text
04 18                readback
04 13, byte 8 = 01   readback
data:
  byte 0  = 80
  byte 9  = brightness
  14..15  = AA 55
04 02                readback
04 F0                no readback
```

Stored RGB table:

```text
04 18                readback
04 23, byte 8 = 09   readback
576-byte table       readback after the complete table
04 02                readback
04 F0                readback
```

For LED index `i`:

```text
i*4 + 0 = light_index
i*4 + 1 = R
i*4 + 2 = G
i*4 + 3 = B
```

The trailer is written as uint16 `0x55AA` at offset `0x23E`. Because the OEM executable is little-endian x86, the bytes on the wire are:

```text
AA 55
```

This exact OEM result overrides the contrary byte order found in one community sample implementation.

## 04 F5 investigation

The OEM key-color readback function is `FUN_0042ae20`.

For RGB mode it constructs:

```text
04 F5
byte 8 = 09
```

and passes the request to the OEM's special feature-report reader.

The mapped sequence is:

1. Send the 64-byte `04 F5` feature report.
2. Perform a short GET_FEATURE for **9 total HID bytes**:
   - 1 report-ID byte
   - 8 payload bytes
3. Check ACK payload byte 3 for `01`.
4. Read nine full 64-byte payload reports.
5. Concatenate them into a 576-byte color table.
6. For every known F108 `light_index i`, read:
   - R at `i*4+1`
   - G at `i*4+2`
   - B at `i*4+3`
7. Finish with `04 02` and readback.
8. The OEM function does not send `04 F0` after this readback path.

The OEM UI looks up `light_index` through its key metadata and ignores the first slot byte when reconstructing the displayed RGB value.

R8 implements this readback as an optional inspection/import operation. It never silently replaces desired state in SQLite.

R8 adds:

- `RgbColor`

The desktop resolves:

```text
key_id -> Layout.led_index -> PerKeyRgbAssignment
```

before the F108 driver sees the request.

## Persistence

R8 uses the existing schema-3 `per_key_lighting` table for RGB values.

Brightness is stored in the existing generic `device_settings` table using:

```text
capability = per-key-rgb
setting_key = brightness
```

Both brightness and colors are replaced in one SQLite transaction.

Black/off values are not stored as rows. An absent per-key color therefore canonicalizes to off in the complete-table writer.

- drag-region selection

- clear selected

- save desired state while disconnected
- hardware application while connected

## Safety

Before hardware transmission:

- every key ID must exist in the active layout
- every colored key must have an LED index
- duplicate key IDs are rejected
- duplicate LED indices are rejected
- LED index 0 and indices overlapping the trailer are rejected
- brightness must be 0-5
- the complete 576-byte payload is built before the first hardware packet is sent

Stored-RGB operations use the serialized Device Manager hardware queue.
