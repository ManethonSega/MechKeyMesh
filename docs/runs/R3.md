# R3: Persistence and desired-state database

## Status

**COMPLETE**

R3 creates the durable local source of truth required before keymaps, macros, per-key RGB, LCD projects and application profiles become editable.

## Principle

```text
MechKeyMesh SQLite database
          |
          v
desired configuration
          |
          v
driver translation
          |
          v
keyboard
```

The keyboard is not assumed to be able to report every configuration value back reliably.

## Configuration ownership

Every persisted configuration is scoped by:

```text
Device model
+
Profile
+
Capability
```

A stable device model is deliberately separate from a transport/connection driver.

For the first implementation:

```text
device_model_id  aula.f108pro
driver_id        aula.f108pro.usb
profile          default
capability       hardware-rgb
```

A future F108 2.4 GHz driver can therefore use the same device-model profiles instead of creating unrelated configuration.

## Schema migrations

R3 starts with three versioned migrations:

```text
schema 1
  devices
  profiles
  lighting
  device_settings
  application_rules

schema 2
  key_mappings
  layer_mappings
  macros
  macro_events

schema 3
  per_key_lighting
  live_lighting
  music_presets
  lcd_projects
```

Migrations run transactionally and are recorded in `schema_migrations`. The SQLite `user_version` is updated alongside the migration record.

An application build refuses to open a database whose schema is newer than it understands.

## Durability settings

The database uses:

- foreign keys
- WAL journal mode
- synchronous FULL
- five-second busy timeout
- transactional migrations
- SQLite quick integrity checks

## First desired-state vertical slice

Onboard F108 lighting is the first configuration feature wired through the persistence layer.

The desktop flow is now:

```text
edit lighting
    |
    v
save desired state to SQLite
    |
    +---- keyboard unavailable ----> keep configuration locally
    |
    v
keyboard Ready
    |
    v
send through Device Manager
```

Saved lighting is loaded back into the editor when MechKeyMesh starts again.

## Exit criterion

R3 closes when automated tests demonstrate that configuration survives:

- application/database close and reopen
- process restart equivalent
- keyboard absence/disconnect because desired state is independent of the HID session
- schema upgrade

without loss or integrity failure.

Physical Windows restart testing may be performed later when hardware access is available, but the database durability path must be deterministic and covered in CI before R3 closes.
