# R7: Fn layer and reset semantics

## Status

**IN PROGRESS**

R7 turns the Fn editor into a genuine second remap layer and defines safe reset behavior without pretending that broader OEM reset operations are understood.

## Core model

```text
Normal
  capability: Keys
  layer id:   normal
  command:    04 11

Fn
  capability: FnLayer
  layer id:   fn
  command:    04 27
```

Both layers use independent desired-state rows and independent 576-byte F108 remap tables.

The proprietary source files themselves are not committed.

Community protocol evidence confirms:

- Normal remap init uses `04 11`.
- Fn remap init uses `04 27`.
- byte 8 of either init packet is `09`.
- both layers use the same 576-byte slot table format.
- the remap trailer is `AA 55`.
- a zero slot means no remap / firmware default.

## Fn layer restrictions

The exact F108 OEM XML contains 104 key records.

All 104 have:

```text
fnlayer_disable = 0
```

Therefore the F108-specific OEM XML does **not** declare any key as blocked by its software-level Fn-disable map.

This is not the same as saying that every native firmware shortcut is safe to overwrite.

MechKeyMesh adds a separate conservative protection policy to preserve important firmware behavior by default.

### Protected native controls

| Device index | Key(s) | Native behavior protected |
|---:|---|---|
| 1 | Esc | Fn+Esc factory-reset shortcut |
| 19-23 | `, 1, 2, 3, 4 | connection-mode controls |
| 38-41 | Q, W, E, R | OS/device-mode controls |
| 37, 67 | Tab, Backslash | main backlight color/effect controls |
| 99-102 | Left, Down, Up, Right | main backlight speed/brightness controls |
| 73, 91, 93, 74 | Left Shift, Left Ctrl, Left Alt, Z | light-bar controls |
| 84, 98, 95, 83 | Right Shift, Right Ctrl, Right Alt, Slash | sidelight controls |
| 78 | B | native light-bar power behavior |
| 92 | Left Win | Windows-lock behavior |
| 96 | Fn | physical layer selector |

These restrictions are a MechKeyMesh safety policy based on documented native firmware functions. They are **not** presented as OEM `fnlayer_disable` flags and are not evidence that the firmware could never override them.

F1-F12 remain available as Fn remapping targets because the OEM exposes an Fn-layer editor and the F108 XML does not disable them.

### Knob and LCD navigation

The multifunction knob has no F108 remap-table `key_index`.

Therefore the R7 remap implementation does not send assignments for:

- knob rotation
- knob press
- LCD menu navigation
- Fn + knob behavior

Those remain firmware-owned.

## Fn activation mode

The OEM English language data contains:

```text
Fn Switch Function
Momentary
Toggle
```

Direct analysis of the supplied OEM binary maps `fn_switch` as:

```text
raw 0 = Toggle
raw 1 = Momentary
```

The function-settings sender uses the separate sequence:

```text
04 18
04 17
00 01
04 02
```

and places `fn_switch` in the settings data packet.

R7 records the exact enum but does **not** enable writing it yet. That settings transaction is not physically verified and the current keyboard value is not reliably readable.

The UI therefore reports the known enum and explicitly says that the current mode is unavailable and setting writes are disabled.

## Reset investigation

### Reset selected

MechKeyMesh editor-only operation.

Selected mappings are changed to `Default`. Nothing is sent until the layer is saved.

### Reset current layer

Safe, implemented operation.

The desired map for the active layer is replaced with an empty map and the complete zero/default remap table is sent for that layer.

For Fn this means:

```text
04 18
04 27
empty/default 576-byte table
04 02
04 F0
```

### Reset key assignments

Safe, implemented operation.

Both desired maps are cleared in one SQLite transaction. Hardware application then sends:

```text
empty Normal table
then
empty Fn table
```

through the serialized Device Manager.

If hardware application fails after the database commit, the local desired state remains authoritative and can be reapplied later.

### OEM "Reset Keyboard"

The OEM language warns that this clears keyboard data.

Binary tracing shows that its handler rebuilds application/profile state and, in wired mode, queues task type 6. Existing reverse-engineering maps task type 6 to sending both mapping layers.

That supports a mapping-reset component, but does not yet establish the complete scope of every subsystem affected by the OEM button.

MechKeyMesh therefore does not expose an operation named "Reset Keyboard" in R7.

### Factory Reset

The OEM has a separate Factory Reset confirmation and a broader handler.

Its complete hardware scope is not yet mapped.

The physical Fn+Esc shortcut is documented as factory reset, but existing hardware investigation also shows that it does not restore overwritten LCD menu graphics. Therefore "Factory Reset" must not be interpreted as restoring every flash region.

MechKeyMesh does not expose a software Factory Reset command in R7.

## Implementation

R7 adds:

- Fn capability advertisement in the F108 driver
- `04 27` Fn-table transmission
- shared table builder for Normal and Fn
- Fn native-control protection
- independent SQLite scopes for Normal and Fn
- transactional multi-layer persistence
- genuine Normal/Fn UI tabs
- independent undo/redo state per layer
- independent mapped-key visualization per layer
- protected-key visualization and explanation
- reset current layer
- reset both key-assignment layers
- OEM Fn activation enum metadata
- explicit gating of unverified Fn-mode setting writes
