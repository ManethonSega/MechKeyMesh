# R12: F108 Pro 2.4 GHz support

Status: software implementation complete; physical USB to 2.4 GHz to USB switch run pending.

## Evidence and transport

The exact OEM configuration names the wireless variant as `F108Pro Dongle`, VID `05AC`, PID `024F`, interface 3. Static analysis of that OEM driver establishes a 32-byte interrupt-report protocol on usage page `FF60`:

- [`kidush/omarchy-aula-f108pro` protocol analysis](https://github.com/kidush/omarchy-aula-f108pro/blob/aa794b2367e0a66223198db3fe132a9505bc1833/docs/protocol.md)
- [`parsiya/f108-pro` device information](https://github.com/parsiya/f108-pro/blob/f7782b02e254490d9c4ae063a8c27cae38be226f/ai-docs/device-info.md)

Packet layout:

```text
byte 0       command
byte 1       length or subcommand
byte 2       chunk index
bytes 3..30  up to 28 data bytes
byte 31      wrapping sum of bytes 0..30
```

The driver accepts a reply only when bytes 0 through 2 echo the request. A dongle with no online keyboard is not exposed as a connected keyboard. This is important because the USB cable and dongle may both remain attached while the keyboard connection switch changes.

## Connection variants

Both transports are candidates of one `aula.f108pro` driver and one `aula.f108pro` device model:

| Connection | Identity | Transport |
| --- | --- | --- |
| USB | `0C45:800A`, usage page `FF13` | 64-byte HID feature reports |
| 2.4 GHz | `05AC:024F`, usage page `FF60`, interface 3 | 32-byte HID output/input reports |

The manager re-runs discovery after removal or a failed health probe. Wireless health uses the read-only `02 00 00` online probe. Battery uses `20 01 00` and refreshes every 15 seconds.

## Capability matrix

The manifest reports the union, while the active `DeviceDescriptor` reports only the capabilities available through the current connection.

| Capability | USB | 2.4 GHz in R12 |
| --- | :---: | :---: |
| Normal keys | yes | yes |
| Fn layer | yes | yes |
| Hardware macros | yes | no |
| Onboard lighting | yes | yes |
| Stored per-key RGB write | yes | yes |
| Stored per-key RGB readback | yes | no |
| Device settings | yes | yes |
| Battery | no | yes |
| LCD | no | no |
| Live RGB | no | no |
| Music lighting | no | no |

Wireless macros are deliberately not exposed in R12. The OEM sender is known, but its unusual extra-chunk and trailer behavior is not physically verified. LCD is explicitly hidden by the OEM wireless menu. Live RGB and music are separate R13 and R14 work.

The desktop hides navigation for unsupported capabilities and disables wireless-only unsupported readback automatically when the connection changes.

## Implemented wireless commands

| Feature | Command |
| --- | --- |
| Online probe | `02 00` |
| Main lighting | `05 10` |
| Device settings | `07 10` |
| Normal keymap table | `10`, 28-byte chunks |
| Fn keymap table | `12`, 28-byte chunks |
| Stored per-key RGB table | `14`, after `05 10` mode `80` header |
| Battery | `20 01` |

All tables are fully built and validated before their first packet is sent.

## Required physical run

1. Start on USB and confirm the app reports USB capabilities.
2. Switch the keyboard to 2.4 GHz without closing MechKeyMesh.
3. Confirm automatic recovery, the wireless VID/PID, battery reading and reduced controls.
4. Apply a representative onboard effect, one Normal mapping, one Fn mapping, stored RGB and one settings change.
5. Verify each change physically and restore it.
6. Switch back to USB without closing MechKeyMesh.
7. Confirm automatic recovery and restoration of the USB capability set.

Until that run is recorded, R12 is not physically verified.
