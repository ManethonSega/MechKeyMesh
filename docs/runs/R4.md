# R4: Universal layout and action engine

## Status

**COMPLETE**

R4 separates physical keyboard geometry, device addressing and logical key behavior before remapping features are implemented.

## Core rule

```text
electrical/device addressing
!=
physical key position
!=
logical action
```

These concepts must remain independent across every supported keyboard.

## Generic layout engine

R4 adds `mechkeymesh-layout` with:

- `Layout`
- `PhysicalKey`
- `CoordinateSpace`
- optional `MatrixPosition`
- optional `GridPosition`
- `LayoutKind`
- validated `LayoutRegistry`

Supported layout kinds are:

- full-size
- 1800 compact
- TKL
- 75%
- 65%
- 60%
- 40%
- Alice
- split
- ortholinear
- custom

The renderer does not contain a full-size keyboard grid. It renders arbitrary x/y/width/height/rotation data supplied by the active layout.

## Universal KeyAction model

The first schema supports:

- Default
- Disabled
- Keyboard key
- Modified key
- Media
- Mouse
- Windows action
- Open application
- Open file
- Open URL
- Send text
- Macro
- Layer action
- Vendor-specific action

The schema is serializable and can later add TapHold, Transparent, OneShot, Chord and TapDance without coupling those behaviors to key geometry.

## AULA F108 Pro first layout

The analyzed OEM `rgb-keyboard.xml` contains 104 `KeyItems`.

R4 converts the interoperability facts into our own layout file:

```text
drivers/aula-f108pro/layouts/f108pro-ansi.json
```

For every physical key the derived layout stores:

- physical rectangle
- source label plus normalized display label
- source HID/code value
- `key_index`
- `light_index`
- `fnlayer_disable`
- source `row_col`

The original OEM XML and artwork are not committed.

Source fingerprints used for this derivation:

```text
rgb-keyboard.xml
SHA-256 7c3f0720bfe97b9ef1dd820e86fb1e621ff20a9a0eeaf6d97b4329a3aa3c3c62

config.xml
SHA-256 c56ddebeabe06c91acfd1224d81b07a166e661cb04d60b4bffdbfc43e0227d07
```

### Matrix evidence rule

The OEM field `row_col` is not assumed to be the electrical switch matrix.

R4 stores it as:

```text
gridPosition
```

and leaves:

```text
matrix = null
```

until the electrical matrix is independently verified.

## Desktop renderer

The Keys page is enabled in R4.

The desktop:

1. requests the registered layout for the active driver through Tauri
2. receives generic `Layout` data
3. creates an SVG using the declared coordinate space
4. renders every key from `PhysicalKey` geometry
5. supports different key sizes, rotations and optional explicit rotation origins
6. exposes physical/device/LED/source-grid metadata when a key is selected
7. supports Ctrl/Cmd additive key selection

The renderer contains no F108 key coordinates.

## Automated validation

R4 tests cover:

- generic layout validation
- schema-version enforcement
- finite geometry and coordinate-space bounds
- explicit shared rotation origins
- duplicate key, matrix, grid, device-index and LED-index protection
- KeyAction validation and JSON round-trip
- duplicate layout-registry protection
- F108 layout JSON parsing
- F108 key count and evidence completeness
- known F108 reference geometry
- known F108 device and LED indices
- explicit absence of unverified electrical matrix values
- F108 driver manifest layout registration

## Exit criterion

R4 is complete when the AULA F108 Pro keyboard is rendered accurately from the registered layout data, with no F108 key geometry hard-coded into HTML/JavaScript, and the generic layout/action model passes Rust and Windows CI.

## Completion record

R4 software acceptance was closed after the final layout/action implementation passed the repository's Linux core checks, full Windows workspace tests, strict Clippy checks and Windows release build. Earlier red workflow runs belong to intermediate R4 commits and are retained by GitHub as historical results; completion is based on the green final PR head. The Windows CI job now publishes `MechKeyMesh.exe` together with a SHA-256 checksum for hands-on review.

## Post-completion hardening

A later architecture audit found several generic weaknesses that did not affect the F108's rectangular zero-rotation layout but would matter for Alice, split and future multi-vendor boards. Those corrections are documented in [`R4-HARDENING.md`](R4-HARDENING.md).
