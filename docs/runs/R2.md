## Driver registry

Each registered driver declares:

- driver ID
- vendor and device name
- VID/PID matchers
- usage page / interface selection constraints
- supported connection types
- implemented capabilities
- transport requirements

The first registered driver remains:

```text
aula.f108pro.usb
VID 0C45
PID 800A
Usage Page FF13
Connection USB
Transport HID feature reports
```

## Safety decisions

### No automatic retry of hardware writes

R2 retries only **device opening** when the error is classified as transient. It does not automatically replay lighting or other device commands after a partial failure. Replaying a non-idempotent protocol transaction can be unsafe.

### Duplicate devices are not selected arbitrarily

If more than one supported keyboard instance is discovered and no explicit selection exists yet, the manager enters `Ambiguous` state instead of opening an arbitrary device.

This is intentional. Explicit multi-device selection belongs to a later run.

### Removal detection does not send probe commands

The F108 driver checks whether the exact HID instance path still exists. R2 does not invent a new F108 protocol command merely for liveness testing.

## Automated reconnect validation

The fake-device regression suite performs **10 simulated disconnect/reconnect cycles** and requires the manager to return to `Ready` every time without concurrent hardware operations or a manager restart.

This does not replace physical HID testing, but it exercises the lifecycle/recovery state machine deterministically in CI.

## Physical test plan

When the AULA F108 Pro is available:

1. start MechKeyMesh without the keyboard
2. connect the F108
3. confirm Ready
4. disconnect it
5. confirm the application remains responsive
6. reconnect it
7. confirm automatic return to Ready
8. repeat disconnect/reconnect ten times
9. close and reopen MechKeyMesh
10. verify the device is rediscovered cleanly

Suspend/resume testing is intentionally deferred to R19.

## R2 completion decision

R2 is closed as the **Device Manager 2.0 software-foundation run**.

The latest branch CI run **38081253305** passed after the final R2 documentation update. Earlier green runs also verified the Rust workspace tests, Linux Clippy, Windows workspace tests, Windows Clippy, Windows release build and explicit `MechKeyMesh.exe` existence check.

Physical AULA F108 Pro hot-plug/reconnect testing remains **deferred**, because the keyboard is not currently available for testing. This is not recorded as a pass. The deterministic fake-device suite covers ten disconnect/reconnect cycles in CI, while real HID acceptance remains a tracked regression gate before a public hardware-supported release.

R2 completion means the production-oriented manager architecture is ready to become authoritative on `main`. It does **not** mean all future device behavior has been physically validated.
